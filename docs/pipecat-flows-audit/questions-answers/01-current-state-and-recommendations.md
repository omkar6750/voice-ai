# Pipecat Flows audit: questions and answers

Checked 2026-10-01 against the six supplied documents, the current Pipecat documentation index, and the repository source. This is an architecture review, not a behavior change. The supplied documents are preserved verbatim in [`../references/`](../references/). Source links below point to the actual implementation. Pipecat links point to its current public documentation. The installed dependency is Pipecat 1.11.0 (`uv.lock`).

## 1. Are we using a flow config to initialize the runner? Declarative or programmatic?

**We use Pipecat Flows, but not Pipecat's declarative `FlowConfig`/`Flow`.** The API stores our own `AgentConfig.flow` shape: a list of nodes with `id`, `prompt`, optional `role_prompt`, `transitions`, tool binding names, action binding names, and flags. The call claim supplies `resolved_config`; `execute_call()` passes it to `driver.prepare()` ([runner.py](../../../packages/voice_runtime/voice_runtime/execution/runner.py)). The native host converts each saved node to Pipecat `NodeConfig` in `_node()` ([native_host.py:104](../../../packages/voice_runtime/voice_runtime/execution/native_host.py#L104)). It constructs a `PipelineWorker` and `TracedFlowManager`, which subclasses Pipecat `FlowManager` ([native_host.py:450](../../../packages/voice_runtime/voice_runtime/execution/native_host.py#L450)); starts `WorkerRunner` ([native_host.py:485](../../../packages/voice_runtime/voice_runtime/execution/native_host.py#L485)); and initializes the manager with the configured initial node when the call begins ([pipeline_lifecycle.py:103](../../../packages/voice_runtime/voice_runtime/execution/pipeline_lifecycle.py#L103)). No YAML file is generated or loaded for a production call, and no Pipecat `Flow` object validates handler references. This is a **programmatic adapter over a custom declarative database schema**, rather than a Pipecat declarative flow.

That distinction matters: the pipeline and runner manage transport, STT, LLM, TTS, and worker lifecycle; `FlowManager` manages node context and tool changes. The application still has to adapt its database config to Pipecat. Pipecat's recommended data-driven route is `FlowConfig.model_validate(data)` or `from_yaml`, then `Flow(config, handlers=...)`, then `FlowManager(..., global_functions=flow.global_functions)` and `initialize(flow.initial_node)` ([Flow Configs](https://docs.pipecat.ai/pipecat/flows/flow-configs), supplied attachment 02). This can be assembled **per call from database data**; YAML is an interchange/example format, not a required file on disk. A significant blocker to a full translation is that our registered tools carry explicit JSON parameter schemas and per-call schema changes (for example the allowed callback roles and `change_node` destinations); Pipecat's ordinary config functions derive parameters from Python signatures/docstrings. Pipecat recommends programmatic `FlowsFunctionSchema` when strict enums or ranges matter ([Flows introduction](https://docs.pipecat.ai/pipecat/flows/introduction#choosing)). Retain a programmatic seam for those tools or prove an equivalent constrained declarative adapter before migration.

**Why current code does this:** the schema already supports versioned tool bindings, JSON schemas, evidence tracking, classifier cadence, callback tool gating, and telephony behavior. Those are visible in code, but the source does not prove the original design motivation. A conversion needs to preserve those capabilities; merely swapping the class name would drop them.

## 2. Are node prompts incorrectly injected as user messages? Do we have one system instruction?

**Yes on the first point.** `_node()` turns `node.prompt` into `{"role": "user", "content": ...}` and also adds a terminal instruction as another user message ([native_host.py:137](../../../packages/voice_runtime/voice_runtime/execution/native_host.py#L137)). A generated opening instruction is separately seeded into `LLMContext` as a user message ([native_host.py:370](../../../packages/voice_runtime/voice_runtime/execution/native_host.py#L370)). Classifier results are also intentionally delivered as user-role context messages ([classifier_runtime.py](../../../packages/voice_runtime/voice_runtime/execution/classifier_runtime.py), [exchange.py](../../../packages/voice_runtime/voice_runtime/execution/exchange.py)). Thus synthetic instructions/results can look like caller turns to the model. This is a plausible cause of conversational confusion, though a production call trace is needed to attribute any particular symptom.

The `system_prompt` is put in LLM service `system_instruction` at construction ([native_host.py:293](../../../packages/voice_runtime/voice_runtime/execution/native_host.py#L293), [llm_factory.py](../../../packages/voice_runtime/voice_runtime/execution/llm_factory.py)). On the initial node only, it is also used as `role_message` **if** `role_prompt` is absent ([native_host.py:108](../../../packages/voice_runtime/voice_runtime/execution/native_host.py#L108)). Other nodes may set a `role_prompt`, which becomes Pipecat `role_message`; therefore it is inaccurate to say the global instruction is necessarily the only system instruction for the whole call. However the UI presents one global prompt plus optional per-node override, and the initial node override can replace the global role. The `prompt_composition` setting exists in the saved schema but is not read by `_node()`; its labels do not currently determine how messages are composed ([agent.py:29](../../../packages/voice_runtime/voice_runtime/contracts/agent.py#L29)).

**Recommended:** expose Pipecat's `role_message` as the provider system instruction. Put the persona and active node objective there on each node. Do not rely on task-message role translation to keep instructions system-level: `task_messages` are appended to conversation context, and adapters can map their roles to user. Keep `task_messages` for intentional context messages (or an empty list), and keep actual caller speech in `user`. Remove the synthetic user-role node and terminal instructions. Decide explicitly how a global persona becomes the initial `role_message`; avoid a second competing service-level instruction. Keep tool results as tool results where possible; classifier outcomes need a separate design because they are not always triggered by a model tool call.

## 3. Do role and task messages replace themselves on transitions or on RESET?

Pipecat 1.11's `FlowManager` sends a nonempty `role_message` as an `LLMUpdateSettingsFrame(system_instruction=...)`; it remains the service instruction until another node sets one. It does **not** append that role string as a normal conversation message. It appends `task_messages` to context under APPEND, and replaces the context message list with the new node's `task_messages` under RESET (installed `pipecat/flows/manager.py`, `_update_context`, lines 841–911). Therefore APPEND retains **earlier task messages as well as dialogue**; it does not automatically remove the old node's task. RESET clears dialogue and old task messages, but the service-level role instruction persists unless replaced. This agrees with [Nodes & Messages](https://docs.pipecat.ai/pipecat/flows/nodes-and-messages) and [Context Strategies](https://docs.pipecat.ai/pipecat/flows/context-strategies).

### Provider role behavior and the node-instruction fix

The Gemini adapter extracts a system/developer message from context as the API system instruction **only when that message is at `messages[0]`**. Later system/developer messages are converted to user-role content. With ordinary conversation already in the context, a node's appended `task_messages` do not become the Gemini system instruction just because they use `role: system` or `role: developer`. OpenRouter likewise declares `supports_developer_role = False`; its OpenAI adapter converts developer messages to user messages. The exact request payload is provider- and adapter-specific, so test the actual configured Gemini and Qwen routes rather than infer behavior from the authoring schema.

The robust native Pipecat path is `role_message`: FlowManager sends it as `LLMUpdateSettingsFrame(LLMSettings(system_instruction=...))`, updating the provider setting directly. Compile each node's stable persona plus current objective into that field. The installed `FlowConfig.Node` still requires the `task_messages` key, but accepts an empty list; keep it empty when the node has no intentional context message. This changes task placement, whereas merely migrating the old prompt into `task_messages` would reproduce the user-context ambiguity. With APPEND, prior dialogue remains, while per-node objectives are replaced in the system instruction on each node entry; do not also append those objectives as task messages.

The pasted recommendation to set a stable persona once in the first node is a sound default for ordinary use, but it does not solve this project's requirement that the active node objective remain system-level. Here, compose the stable persona and current node objective into each node's `role_message`. That makes the active objective replace on node entry without adding it to caller context. For long lead calls, APPEND retains dialogue and state-backed evidence; do not also append old objectives as task messages. Use native summarization or a deliberate RESET only when history needs to be shortened.

## 4. Will Gemini and Qwen map roles automatically?

**Pipecat handles provider adaptation, with an important caveat.** The flow docs say role messages become the provider's system instruction and task messages use OpenAI-style roles ([Nodes & Messages](https://docs.pipecat.ai/pipecat/flows/nodes-and-messages#cross-provider-compatibility)). Our Gemini path uses `GoogleLLMService`; its settings include `system_instruction` ([llm_factory.py](../../../packages/voice_runtime/voice_runtime/execution/llm_factory.py)). Qwen is normally selected through Groq or OpenRouter in this code, not a direct Qwen-specific service. The installed OpenRouter service sets `supports_developer_role = False` and its OpenAI-compatible adapter converts unsupported developer messages rather than guaranteeing a native developer channel (`.venv/Lib/site-packages/pipecat/services/openrouter/llm.py`, line 40; `openai/base_llm.py`, line 331). **Do not promise that a Qwen request receives a true developer role.** The stable role message is the safer place for high-priority rules. Verify actual serialized request roles for each chosen provider/model in a focused adapter test before rollout. Speech-to-speech models are outside Flows' supported setup; our pipeline is cascaded STT → text LLM → TTS.

## 5. Why is the initial node greeting? Can a caller jump to callback or closing?

The backend does **not** require the name `greeting`; it requires `initial_node` to name an existing node and all nodes to be reachable with a path to a terminal ([agent.py:29](../../../packages/voice_runtime/voice_runtime/contracts/agent.py#L29)). The UI has an editable Initial node selector ([FlowPanel.tsx:168](../../../apps/dashboard/src/pages/agents/FlowPanel.tsx#L168)). The **seeded starter agent** sets `initial_node="greeting"`, teaches the model to call `change_node`, and binds that tool ([organization_seed.py:74](../../../apps/api/voice_api/services/organization_seed.py#L74)). The word greeting also labels the first evidence exchange, regardless of the selected node ([pipeline_lifecycle.py:103](../../../packages/voice_runtime/voice_runtime/execution/pipeline_lifecycle.py#L103)); this is an evidence label, not a forced graph node. Existing saved agents may independently be configured with greeting. No Elevated Box database snapshot was available in the repository, so its specific initial-node value cannot be verified here.

For lead qualification, allow greeting → discovery **or** callback **or** closing, plus callback and closing exits from discovery/qualify as desired. The saved graph currently permits such edges, though the model must call `change_node`. A terminal should be a **closing step with post-speech hangup**, not simply a node with no outgoing edges; our current code sets a Pipecat post-action for terminal nodes ([native_host.py:211](../../../packages/voice_runtime/voice_runtime/execution/native_host.py#L211)). Consider declining/busy/voicemail paths separately if the call product needs them.

## 6. Why `change_node`? Could node functions, edge functions, and branch tables replace it?

Today every saved node lists allowed destination IDs in `transitions`; `_node()` exposes one `change_node(node)` function and narrows its argument enum to those IDs. Its handler checks the selected destination and returns the next `NodeConfig` ([native_host.py:114](../../../packages/voice_runtime/voice_runtime/execution/native_host.py#L114), [tool_dispatch.py:108](../../../packages/voice_runtime/voice_runtime/execution/tool_dispatch.py#L108)). This is a programmatic Flows edge and is not entirely outside Pipecat, but it makes the LLM select a generic destination and often requires a second tool call after a business tool.

Pipecat declarative config supports a tool with a fixed `transition_to`, a `transition_only` tool for a pure choice, and a branch table over a handler result field ([Functions](https://docs.pipecat.ai/pipecat/flows/functions)). A qualification handler can return `{"status": "qualified"}` and `TRANSITION_IN_YAML`; the graph routes `qualified → book_callback`, `unqualified → closing`, and `needs_more_information → discovery` without the model reading a classifier result and issuing `change_node`. **The model still decides when to call the tool**, and a separate asynchronous classifier result cannot automatically drive a branch table unless wrapped in an awaited handler or followed by a programmatic transition. Branch outcomes must be bounded and have explicit error/unmatched behavior. A dynamic destination determined outside the conversation may still justify a programmatic node change.

## 7. Are pre-actions/post-actions and global functions used properly?

Terminal completion uses a real Pipecat `post_actions` function, so that part already uses the library's sequencing after initial response/TTS ([native_host.py:211](../../../packages/voice_runtime/voice_runtime/execution/native_host.py#L211), [Actions](https://docs.pipecat.ai/pipecat/flows/actions#action-timing)). The saved `entry_actions`/`exit_actions` are different: `TracedFlowManager._set_node()` runs them in its own order alongside entry/exit classifiers **before** calling Pipecat's `_set_node()` ([flow_manager.py:53](../../../packages/voice_runtime/voice_runtime/execution/flow_manager.py#L53)). An entry action can stop node installation. `NativeNodeActions` executes only allow-listed bound handlers and special-cases `end_call` ([node_actions.py](../../../packages/voice_runtime/voice_runtime/execution/node_actions.py)). Pipecat's normal `pre_actions` cover once-on-entry work; `post_actions` cover once-after-initial-response work. They are **not a general node-exit hook**. Preserve a small custom exit hook if exit-time classification is a genuine requirement, but move ordinary entry and post-response actions to Pipecat actions. Existing evidence/telephony semantics need tests before removal of the wrapper.

No `global_functions=` argument is passed to the current manager ([native_host.py:461](../../../packages/voice_runtime/voice_runtime/execution/native_host.py#L461)). Tools are repeated in each node's `tool_bindings`. A native global function is appropriate for universally safe functions such as constrained fact capture or a caller-requested callback option, after deciding whether it should really be available in terminal and compliance-sensitive nodes. Global functions can themselves transition ([State Management](https://docs.pipecat.ai/pipecat/flows/state-management#global-functions)). Avoid exposing unrestricted generic actions in every node. Adding new registered handlers today requires registry, API binding/validation, runtime dispatch, and often UI work; that is a real integration boundary for security/evidence, but the current central dispatch and action allow-list add more wiring than Pipecat's direct-function model.

## 8. Can operators define fact-capture tools and preserve facts through RESET?

Yes, with a constrained product design. `FlowManager.state` is already seeded with temporal and allowed contact values ([native_host.py:353](../../../packages/voice_runtime/voice_runtime/execution/native_host.py#L353)), but our normal tool handlers do not provide a general operator-configured `collect_<fact>` facility. The example `record_favorite_color` in the supplied docs **prints and returns** the color; by itself it does **not** save it to state. The state-management example explicitly does `flow_manager.state["party_size"] = size` ([State Management](https://docs.pipecat.ai/pipecat/flows/state-management#cross-node-state)). Design typed, named slots with descriptions and validation; offer generated tools or one constrained `record_fact(key, value)` whose key is an enum. Store `state[slot]` only after validation, and make needed facts visible to later nodes via `{{ slot }}` or a concise summary. State survives an LLM context RESET for the call, but is **not automatically durable storage**; persistence to run records/contact data requires an explicit trusted service and retention rules. Outcome flags such as `callback_booked` and `whatsapp_sent` should be set from successful backend tool results, not from the model's claim. Placeholder keys missing at node entry raise `FlowError`, so initialize optional slots or gate the node.

## 9. Should we set `filter_incomplete_user_turns=True` in VAD?

It is **not a VAD parameter**. It belongs to `LLMUserAggregatorParams` and is currently absent from `build_user_aggregator_params()` ([native_helpers.py:202](../../../packages/voice_runtime/voice_runtime/execution/native_helpers.py#L202)). The installed Pipecat 1.11.0 marks the boolean deprecated since 1.2 and translates it to `FilterIncompleteUserTurnStrategies` (`.venv/Lib/site-packages/pipecat/processors/aggregators/llm_response_universal.py`, lines 151–188, 672–681). This strategy asks the **main LLM** to prepend a completion marker to its normal response; it is not a separate classifier call for every utterance. An incomplete marker suppresses that response and may trigger another LLM re-prompt after a timeout, adding delay and potentially more inference. Proposed rollout: expose `filter_incomplete_user_turns` in agent config with default `false`, preserving Smart Turn v3 behavior for the default/control group; map only experiment-group `true` to the current strategy API, not the deprecated boolean parameter. Record cohort and compare quality/latency before changing the default. This field is an aggregator setting, not a VAD parameter.

## 10. Other deviations and risks found

1. **Split instruction ownership.** `system_prompt` is service settings, optional initial `role_prompt` is a Flow update, and node/terminal/kickoff instructions are user messages. Establish one explicit precedence model and verify provider requests.
2. **Accumulating step instructions.** APPEND retains previous task messages. Merely changing their role to developer or system does not reliably make later task messages system instructions across adapters, and does not remove old objectives. Compile active node objectives into `role_message`; test direct callback/closing jumps and serialized provider payloads.
3. **Private Flows overrides.** `TracedFlowManager` overrides `_set_node` and `_create_transition_func`, both underscored methods ([flow_manager.py](../../../packages/voice_runtime/voice_runtime/execution/flow_manager.py)). These are upgrade-sensitive. Prefer public callbacks/actions where possible and keep narrow version-pinned tests for unavoidable evidence interception.
4. **Classifier result injection.** Entry/exit/cadence results are synthetic user-role messages, and cadence adds to the next turn's context ([classifier_runtime.py](../../../packages/voice_runtime/voice_runtime/execution/classifier_runtime.py)). Do not automatically turn every result into a branch transition; specify which classifier outcome controls which edge and when it is available.
5. **Two kinds of ending.** A terminal node post-action ends after the initial response; the `end_call` tool ends through a separate path. Consolidate the product semantics while preserving graceful telephony cleanup and result evidence.
6. **Opening coupling.** A verbatim greeting forces `respond_immediately=false` in schema validation ([agent.py:183](../../../packages/voice_runtime/voice_runtime/contracts/agent.py#L183)), while an absent greeting creates a synthetic user kickoff. The proposed direction is to remove the separate verbatim `greeting` field and put the opening in the initial node's `task_messages`; use `tts_say` pre-action only when exact wording is required. Preserve explicit `respond_immediately` behavior for outbound call timing and migrate existing saved greetings before removing the legacy field.
7. **Graph constraints exceed Pipecat config.** Our schema requires all nodes reachable and every node to have a terminal path. Keep those useful product validations if migrating to native `FlowConfig`; Pipecat config validation alone will not preserve them automatically.

## 11. Should we use Pipecat's visual flow editor?

The official [`pipecat-flows-editor`](https://github.com/pipecat-ai/pipecat-flows-editor) project is a visual React Flow canvas for native Pipecat `FlowConfig` YAML. It supports editing messages, tools, actions, branch routing, initial node, validation, and export. Its repository describes browser-local draft storage and file import/export, not authenticated persistence to our API. Its integration guide documents loading YAML with `FlowConfig` and joining it with Python handlers through `Flow`; it also explains that direct tool descriptions and schemas come from handler signatures/docstrings, so it does not expose our versioned registered-tool schema forms.

The dashboard already has an Initial node selector in `FlowPanel`; it is not currently configurable during the new-agent creation flow, which seeds `initial_node: "greeting"` ([agents/index.tsx](../../../apps/dashboard/src/pages/agents/index.tsx#L86)). Node order follows the `flow.nodes` array; there are no reorder controls. Add a creation-time initial-node choice (or default it to the first-created node and make the choice visible), then add reorder controls. For a complete graph canvas, adapt or fork the official editor after the API/runtime config moves toward Pipecat FlowConfig, or build a deliberate translation layer while retaining our versioned handler schemas, Clerk-authenticated saves, revision checks, and validation. Using the hosted standalone editor as the production editor would not save into our database or honor our auth/revision model.

## Recommended lead-qualification design

Set the persona, non-negotiable call rules, and that node's current objective in each node's `role_message`, so they reach the provider system-instruction channel. Keep `task_messages` empty unless the node intentionally needs to add context messages; never put caller-facing instructions there when they must remain system-level. Use explicit tool-linked transitions, including an immediate greeting → callback option. Use branch tables for synchronous qualification and booking outcomes; keep routing decisions deterministic after the tool returns. Make `closing` perform its goodbye, then use a Pipecat post-action to end the call. Save validated facts and backend-confirmed outcome flags in `FlowManager.state`; expose only the facts each node needs. Start with APPEND for a short call; use native summarization or a carefully designed RESET for long calls.

The YAML in [`../plans/example-lead-qualification-flow.yaml`](../plans/example-lead-qualification-flow.yaml) demonstrates this shape and **passed both `FlowConfig.from_file` structural validation and `Flow(config, handlers=...)` reference validation on installed Pipecat 1.11.0** using [deliberately inert handler stubs](../plans/example_lead_qualification_handlers.py). It is illustrative, not an export of Elevated Box. An end-to-end call remains unverified because the handlers do not perform business work and the Elevated Box published snapshot was not available in this repository. An actual agent-specific export should be generated from its published configuration after access to that snapshot is available.
