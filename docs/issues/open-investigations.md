# Open investigations

These are limitations or unfinished investigations from development, reviewed
October 15, 2026. They are not implemented fixes or newly approved architecture.

## OPEN-001 Sarvam playback text

The assistant aggregator is after transport output, but Sarvam TTS text frames do
not provide precise word-to-audio alignment in this integration. A generated reply
can contain words not played before interruption. Clearing the voicemail speech
gate fixes stale playback; it does not establish the exact text the caller heard.

Next reproduction: use a deterministic audio stream and controlled interruption,
record which text frames cross the real output boundary, and compare context with
the acknowledged playback. Any duration-to-character approximation must be labeled
approximate and distinguish generated bytes, queued bytes and output acknowledgments.
Serial writes do not prove remote playback. No alignment fix is claimed here.

Source: `execution/speech.py`, `native_host.py`, `voicemail.py`. Related existing
gate tests are in [ISSUE-003](ISSUE-003-stale-greeting.md); they do not close this issue.

## OPEN-002 Serial response ownership

The earlier investigation reported a command receiving `NO CARRIER` and leaving a
trailing `OK` for the next command. This could misattribute a CEER or registration
response and explain missing release readings. The investigation has not established
a committed fix for that sequence in this checkout.

Next test: feed fragmented `NO CARRIER`, trailing terminator and following command
response through the actual serialized reader. Assert command ownership, URC capture
and next-response content. Keep the existing single-reader lock and bounded deadlines.
Do not claim all missing CEER readings share this cause without each run's evidence.

Source: [sim7600.py](../../packages/voice_runtime/voice_runtime/telephony/sim7600.py).
Related outcome coverage: [ISSUE-006](ISSUE-006-call-outcomes.md).

## OPEN-003 Conversation quality

Real tests showed repeated acknowledgments, unnecessary discovery, internal tool
narration, inconsistent language and poor transition continuation. Config edits can
improve a particular call without proving broad improvement. Respond-on-entry,
transition instructions, tool availability and retained context must be inspected
before attributing a symptom to the summarizer or a provider.

Next work: execute candidate versions against schema-validated scripted caller
scenarios with fake tool results. Check tool/routing outcomes deterministically and
grade relevance/naturalness with an evidence-backed rubric. Version cases and judge
settings. This harness is not implemented by the documentation update.

## OPEN-005 Existing test expectations conflict with current policies

The October 15 focused run produced 170 passes and two failures. Both failures
reproduced in isolation; no application code or test expectation was changed here.

- `test_provider_failover.py::test_groq_fallback_preserves_current_node_instruction_and_user_task`
  injects HTTP 400 and expects a fallback response. Current retry classification
  treats that BadRequestError as non-transient and propagates it before the test's
  context assertions. The current test therefore does not verify the intended
  context invariant. A future repair should exercise an eligible transient failure
  and retain a separate assertion that invalid requests do not trigger retries.
- `test_terminal_node_shutdown.py::test_terminal_queue_failure_keeps_failure_cause_with_completed_terminal_outcome`
  expects `execution_status=completed` after shutdown queuing fails. The current
  termination policy reports `failed`, preserving the pipeline failure. Reconcile
  the test with the accepted failure/completion policy before changing either.

These are observed mismatches, not fresh proof of a live provider or modem bug.
See [verification](verification.md) for scope and commands. Until reconciled, do not
advertise the linked suite as fully passing.
