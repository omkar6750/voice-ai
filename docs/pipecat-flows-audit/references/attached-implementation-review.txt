Findings
1. [P1] A WhatsApp window check can use a different connection from the send. The 24-hour inbound-message queries filter by sender and time, but not by connection_id. The text-send path then resolves the first enabled WhatsApp connection when none is specified. In an organization with multiple connections, an inbound message on one account can authorize a send through another. Scope both the window check and send to the tool’s pinned connection. 2. [P1] Non-LLM/STT errors are attributed to TTS. In the observer’s ErrorFrame handler, anything that is not the LLM or STT falls through to "tts". A transport or other processor error can therefore be reported as a TTS failure and can incorrectly fail an active TTS span. Add an explicit unknown/runtime category for unrecognized processors. See [observer.py (line 153)](/C:/Users/Omkar/Desktop/voice-ai/packages/voice_runtime/voice_runtime/execution/observer.py:153).
3. [P1] “Avg first token” includes non-LLM latencies. The run summary averages ttfb_ms across every span, then labels the result “Avg first token.” STT and TTS can also report TTFB, so this number is not an LLM first-token average. Filter to LLM spans and label the measurement precisely. See [detail.tsx (line 163)](/C:/Users/Omkar/Desktop/voice-ai/apps/dashboard/src/pages/runs/detail.tsx:163) and [detail.tsx (line 330)](/C:/Users/Omkar/Desktop/voice-ai/apps/dashboard/src/pages/runs/detail.tsx:330).
4. [P2] Provider labels are inconsistent. STT spans hard-code sarvam; TTS spans store the service class name, such as CartesiaTTSService, instead of the configured provider ID. The host already passes normalized provider names into the observer. Use those values when creating spans. 5. [P2] The inspector shows many permanently unavailable fields. A selected span renders interruption, token, audio, and OTel rows for every category, even when those measurements do not apply or were not emitted. For example, playback spans will show token fields as “Not recorded.” Render applicable non-null measurements first; put missing-measurement coverage in a compact expandable section. 6. [P2] The observer omits useful Pipecat metrics. Metrics are enabled, and the observer records TTFB, TTFA, TTFAT, processing time, and LLM token usage. It does not currently persist STT audio seconds, TTS character usage, or text aggregation latency. Pipecat documents these as separate per-interaction metrics, alongside the existing metrics. Capturing them would help separate recognition, sentence buffering, synthesis, and provider usage. Pipecat Metrics
7. [P2] STT end-of-turn latency is not directly measured or surfaced. The current pipeline has VAD stop and finalized transcription events, so it can measure speech-end-to-final-transcript latency using a monotonic clock. Pipecat calls this TTFS and distinguishes it from TTFB; it is a tuning input, not a built-in runtime metric. The current agent contract exposes a fixed Sarvam model, VAD controls, and Smart Turn stop strategy, but no TTFS measurement in the run view. Pipecat STT Latency Tuning
8. [P2] Error evidence loses Pipecat’s failure classification. The observer records ErrorFrame text or exception details, while pipeline failure cancels the worker. It does not appear to persist Pipecat’s ErrorCategory or processor usability state, so operators cannot readily distinguish a recoverable outage from invalid credentials, an invalid model, or an application/tool error. Fail-fast shutdown is sensible for a broken call, but preserve the category and retryability in the diagnostic. Pipecat’s current guidance centers on ErrorCategory and is_usable. Pipecat Error Handling
9. [P2] Voicemail detection is not wired into the host. The code handles user idle and call termination, but I found no VoicemailDetector use. That means the system has no dedicated person-versus-voicemail decision before treating an outbound answer as a conversation. Pipecat’s documented pattern classifies after STT and gates TTS so the agent does not talk over a voicemail greeting. Pipecat Voicemail Detection

End-to-end path and current behavior
- Browser: the dashboard creates a browser session, obtains a short-lived ticket, and opens the session WebSocket. That path runs the host in-process and cleans up browser resources separately from telephone calls. It is distinct from the generic POST /runs endpoint, which creates a queued run; the dashboard’s live test uses /browser-sessions.
- SIM7600: the call is claimed before side effects. The driver opens and checks the modem, verifies PCM format, prepares the host/audio path, dials, and monitors call state. Cleanup hangs up and verifies idle/disconnected state before the endpoint is released.
- Twilio: authenticated media callbacks claim the run before starting its pipeline. The custom media session owns ordered stream writes, final playback marks, REST completion, and provider readback. Uncertain external outcomes are not retried as new calls.
- Evidence: the runtime streams validated records through a durable spool and tracks evidence completeness separately from call completion. This is a solid basis for the run history, though provider spans need the attribution and metric fixes above.
- Transcripts: caller messages are persisted by ExchangeTracker.user_message; assistant messages come from on_assistant_turn_stopped, retaining interruption state. The supplied Pipecat guide uses on_user_turn_stopped for standard pipelines and recommends on_user_turn_message_added for realtime mode, where stopped-message content may be None. Your current pipeline is standard STT→LLM, so document why the message-added event is intentional or align it with the standard event after checking the pinned SDK behavior. Dashboard and documentation recommendations
For a richer run debugger, organize the evidence around call setup, caller speech, inference/tool execution, synthesis/playback, and termination. Add TTFS and the missing usage/aggregation metrics; keep measured values distinct from unavailable values. In the inspector, show fields that apply to the selected event, and link diagnostics to the provider operation where possible. Keep channel-specific playback evidence explicit: local output completion, Twilio mark/readback, and browser resource cleanup prove different things.
