# Proposed implementation sequence

This is a plan for review, not a claim that the runtime changes are complete. Keep each slice independently testable against a published agent snapshot and call evidence.

1. **Capture baseline.** Export the Elevated Box published agent configuration with secrets redacted, record selected provider/model and prompt roles from one controlled call, and add scripted scenarios for greeting → discovery, greeting → callback, any node → closing, qualification outcomes, and terminal speech/hangup. The database snapshot is required for an exact Elevated Box YAML example.
2. **Fix instruction roles and opening ownership first.** Keep `role_message` as Pipecat's exact field for the provider system instruction. Put the stable persona and the active node objective in each node's `role_message`; do not migrate current node prompts into `task_messages`, because Pipecat appends task messages to conversation context and provider adapters may map their roles to user. Keep `task_messages` available for deliberate context messages and default it to an empty list when a node has no such messages. Remove synthetic `user` node and terminal instructions. Remove the separate verbatim `greeting` setting and its rendering/direct-TTS path; the initial node's `role_message` owns the conversational opening. Use `pre_actions: [{type: tts_say, ...}]` only for deliberately exact fixed wording. Preserve `respond_immediately` behavior for outbound call timing. Keep a compatibility reader for published revisions while converting `prompt` and `greeting` into the initial or corresponding node `role_message` (or a TTS action only where exact wording is required). Verify serialized Gemini and OpenRouter/Qwen requests and conversation behavior. The global `system_prompt` can remain temporarily as a migration source for the initial `role_message`, then be removed as a competing authoring field once converted.
3. **Make edges first-class.** Add node/edge function references and fixed or branch-table `transition_to` to the saved graph, while retaining the existing versioned tool registry. Translate eligible published graphs to Pipecat `FlowConfig` and construct `Flow(config, handlers=...)` before a call starts. Keep product graph reachability/terminal validation. For tools requiring the registry's strict JSON Schema, callback-role enums, or other per-call schema changes, retain a programmatic `FlowsFunctionSchema` seam unless a validated adapter can preserve those constraints. Migrate `change_node` bindings to named transition-only edges and tool-linked edges. Preserve the old reader until all active revisions have a translation.
4. **Use native actions and shared functions.** Extend the versioned flow schema and dashboard to configure ordered Pipecat `pre_actions` and `post_actions`, including the built-in `tts_say` action with literal or state-placeholder text and `append_text_to_context`. Adapt them into each native `NodeConfig`; today the editor does not expose these actions and `TracedFlowManager` runs custom entry/exit bindings instead. A node can run `tts_say` first, then a `function` pre-action for work such as retrieval or another transition-time operation using query/facts already saved to state. The LLM then runs once with the operation result to produce the useful response, avoiding an LLM turn just to say fixed text. By default, inference follows pre-actions; `respond_immediately: false` waits for caller input and does not automatically continue into another node inference. Use `post_actions` for work after the node's initial LLM response and TTS. Retain only exit hooks that cannot be expressed by Pipecat.

   Add `global_functions` (or equivalent global tool bindings) to the saved flow contract and dashboard, resolve them through the existing versioned tool registry, and pass them to `FlowManager(global_functions=...)`. These are model-callable tools exposed on every node, so only genuinely safe and useful cross-node tools belong there. They are not automatic transition hooks: use pre/post actions for work that must run on node entry or after a response. A global function may itself have a transition or branch table when its result should route the flow. Preserve evidence and graceful telephony shutdown. Reduce private `FlowManager` overrides and pin tests to Pipecat 1.11 behavior where interception remains necessary.
5. **Add structured state.** Add a `fact_slots` collection to the versioned agent config. Each slot has a stable key, operator description, value type, optional enum/range constraints, and the nodes where it may be captured. Compile each slot into a distinct model-facing capture function with a narrow JSON Schema (for example, `record_budget_range(value: string)`), but route all of them through one approved backend handler that binds the configured key, revalidates the value, and writes only that slot to `FlowManager.state`. Do not let the model submit arbitrary state keys. Surface slot editing and per-node availability in the dashboard; include generated tools in Pipecat function registration and call evidence. Seed defaults for optional placeholder values. Map backend-confirmed tool outcomes to system-owned flags. Define if/how caller facts persist outside the call; `FlowManager.state` itself is session memory, not durable storage. Show state in post-RESET prompts via placeholders or a short summary, with checks for missing values and sensitive data.
6. **Improve flow editing UX.** Keep `initial_node` configurable when creating an agent as well as when editing one (the current FlowPanel already lets an editor change it; the creation default is hard-coded to `greeting`). Add drag-and-drop or move controls to reorder nodes and persist the node array order. Compare a small native reorder control with adapting the official [Pipecat Flows Editor](https://github.com/pipecat-ai/pipecat-flows-editor) canvas. The upstream editor edits native Pipecat `FlowConfig` YAML and exports YAML; it is browser-local and has no authenticated backend save integration. Our contract and versioned tool registry have additional fields and strict schemas. Prefer borrowing/adapting its canvas and validation after the runtime config migration, or first add a deliberate import/export adapter; do not send users to its standalone hosted editor as the production editing flow.
7. **Add incomplete-turn filtering as an A/B option.** Add a config field named `filter_incomplete_user_turns`, default `false` so existing calls continue using Smart Turn v3 alone. For calls explicitly assigned to the experiment group, map `true` to Pipecat's current `FilterIncompleteUserTurnStrategies` API rather than the deprecated boolean parameter. It asks the main LLM to emit a completion marker as part of its normal response; incomplete markers suppress speech and may trigger a later LLM re-prompt. Assign experiment/control cohorts deliberately and record the setting with call evidence. Compare interruption/resume behavior, premature responses, latency, re-prompts, and call completion before considering a default change. This is an aggregator turn-completion option, not a VAD parameter.

7. **Incomplete-turn filtering** is implemented as `filter_incomplete_user_turns: false` by default. When enabled, `build_user_aggregator_params()` wraps the configured start/stop strategies in Pipecat's `FilterIncompleteUserTurnStrategies`. Cohort assignment and evidence comparison are still needed before a meaningful A/B experiment; this is an aggregator option, not VAD.

8. **Function transitions and branch tables** are implemented with Pipecat's `functions` and `transition_to` fields. The editor attaches registry tools and supports fixed targets and `{field, cases, default}` branch tables. Runtime handlers retain the versioned strict JSON schemas and return `TRANSITION_IN_YAML`, allowing Pipecat Flow to choose the result destination.

9. **Global functions and fact capture** are wired through Pipecat `Flow.global_functions` / `FlowManager(global_functions=...)` and constrained `record_<key>` tools. Fact values remain in `FlowManager.state` across context resets during the call; durable persistence and backend-confirmed status flags remain future work.

The [example YAML](example-lead-qualification-flow.yaml) and [reference-validation handler stubs](example_lead_qualification_handlers.py) show the desired Pipecat structure. They are illustrative and cannot book a callback or record a fact in production.
